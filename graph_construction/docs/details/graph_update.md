# 导航图增量更新原理与优化方案

> 状态: 第一阶段已实现, 待 Unity 长距离回归
>
> 更新时间: 2026-07-21

## 1. 文档目的

本文解释 WildOS 导航图构建模块的职责、当前实现、不同项目实现之间的差异、现有性能问题和后续优化方向

本文重点回答以下问题:

- 为什么输入的高程图大小固定, 导航图更新时间仍会随任务距离增长
- 什么是局部几何地图、持久导航图和真正的局部增量更新
- 论文、NASA-JPL 官方实现、社区 Python 实现和本项目当前实现有什么区别
- 后续如何在不丢失历史路线的前提下, 只更新当前局部区域

## 2. 模块职责

导航图构建模块把机器人附近固定大小的局部 `GridMap` 转换成一张长期保存的稀疏导航图

```text
局部高程图和可通行图
  -> 地图分类和距离场
  -> 更新当前局部节点
  -> 补充新节点
  -> 更新 Frontier
  -> 更新局部连接边
  -> 保存到持久导航图
  -> 发布 NavigationGraph
```

两类地图的职责不同:

- 局部 `GridMap` 表示机器人当前能够可靠观察到的地面、障碍和未知区域
- 持久导航图表示机器人已经探索过的路线、节点、连接关系和探索边界记忆

局部地图会跟随机器人滚动, 持久导航图不会因为局部窗口移动而清空

## 3. 正确的增量更新含义

真正的增量更新包含两层含义:

1. 历史结果增量保存
2. 每帧计算也只处理受当前局部地图影响的数据

只满足第一项还不够

如果历史节点虽然被保存, 但每帧仍遍历全部历史节点和全部历史边, 那么机器人走得越远, 每次更新时间仍会越来越长

理想状态是:

```text
当前局部窗口覆盖的节点和边 -> 更新
刚离开窗口的活动状态 -> 处理一次
远处历史节点和历史边 -> 原样保存, 本帧不访问
```

## 4. 论文和不同实现的对比

### 4.1 WildOS 论文

WildOS 论文使用局部几何地图增量维护持久稀疏导航图

论文的主要步骤是:

1. 更新已有节点的自由半径和探索半径
2. 在当前局部 free 区域采样新节点
3. 检测当前局部 Frontier 并分配给附近图节点
4. 在局部可靠区域建立无碰撞边

论文中的伪代码主要描述算法语义, 没有要求工程实现必须每帧线性扫描完整历史图

参考:

- [WildOS 论文](https://arxiv.org/abs/2602.19308)
- [WildOS 项目主页](https://leggedrobotics.github.io/wildos/)

### 4.2 NASA-JPL 官方 C++ 实现

官方 `graphnav_mapper` 的核心更新范围是局部的

它首先根据地图中心和地图长度, 通过 KD-Tree 查询 `nearby_nodes_in_map`, 后续节点更新、Frontier 清理和边检查主要围绕这个局部节点集合进行

核心逻辑:

```text
局部地图中心和半径
  -> KD-Tree 查询附近节点
  -> 更新附近节点
  -> 在局部地图中采样新节点
  -> 查询 Frontier 附近 owner
  -> 清理附近 Frontier
  -> 检查附近节点已有边和半径内候选边
```

远处历史节点和边不会因为当前局部地图不可见而被删除或重新验证

官方实现仍有两类全局成本:

- 新节点加入后可能重建全局 KD-Tree
- 发布 ROS 消息和 RViz Marker 时仍转换完整导航图

官方实现使用 C++, 因此这些全局操作在中等图规模下影响较小, 但从复杂度上仍不是完全固定耗时

参考:

- [官方 mapper.cpp](https://github.com/nasa-jpl/nebula2-wildos/blob/main/graphnav_mapper/src/mapper.cpp)
- [官方 navigation_graph.cpp](https://github.com/nasa-jpl/nebula2-wildos/blob/main/graphnav_mapper/src/navigation_graph.cpp)

### 4.3 社区 Python 实现

本仓库保存的社区参考实现位于:

```text
external_references/nebula2-wildos-main_ws/graphnav_builder
```

它对地图解码、时间同步、TF、碰撞检查和运行诊断处理得比较完整, 但核心更新仍有明显的全局遍历:

- `update_nodes` 每帧遍历全部节点
- 节点删除后重新编号, 并重建全部边索引
- 采样、Frontier、建边和当前节点查询分别重建全局空间哈希
- 历史 Frontier 每帧遍历全部 owner
- 历史边每帧全部验证
- 新边构建从全部节点开始
- 每个有效地图帧都发布完整导航图

因此该实现主要做到的是历史图不丢失, 并没有做到核心计算量只与局部窗口相关

社区实现值得借鉴的部分:

- 地图和 odom 时间同步
- 使用消息时间对应的 TF
- 处理不过来时丢弃旧地图, 优先处理最新地图
- 全 unknown 地图不破坏历史图
- 调试可视化默认关闭或单独限频
- 没有订阅者时不构造 Marker
- 细分每个建图阶段的耗时

### 4.4 本项目当前实现

当前实现位于:

```text
graph_construction/graph_construction
```

相对社区 Python 版本, 当前实现已经具备以下优点:

- 节点使用稳定 `node_id`, 删除节点不需要重新编号全部节点
- 节点使用字典保存, 历史身份和 UUID 稳定
- 当前局部候选边使用 KD-Tree 近邻查询
- 普通节点限制最大邻边数量, 避免近似全连接
- 历史边在局部窗口变 unknown 时不会被误删
- 轨迹使用分桶索引过滤已访问 Frontier

但当前仍存在以下全局操作:

- `_update_existing_nodes` 遍历全部历史节点, 再判断是否位于当前窗口
- `_sample_new_nodes` 每帧用全部历史节点建立临时 KD-Tree
- Frontier explored-area 索引每帧从全部节点重建
- 历史 Frontier 验证遍历全部节点
- Frontier owner 索引每帧从全部节点重建
- 建立局部边前先遍历全部节点筛选窗口内节点
- `merge_historical_edges` 每帧遍历全部历史边
- 当前节点兜底查询可能对全部节点排序
- ROS 消息转换每帧排序并转换全部节点和边
- RViz Marker 每帧重新生成完整历史图

所以当前实现可以概括为:

> 只修改局部结果, 但为了找到、验证和保留这些结果, 每帧仍多次扫描全局历史

## 5. 当前更新流程

当前 `SparseGraphBuilder.update` 的主要过程如下:

```text
固定大小 GridMap
  -> 清理高程尖峰
  -> 修补脚下盲区
  -> 计算机器人可达 free 分量
  -> 计算 obstacle 和 unknown 距离场
  -> 扫描全部历史节点并更新窗口内节点
  -> 在当前窗口采样新节点
  -> 扫描局部栅格检测 Frontier
  -> 使用全局节点索引分配和验证 Frontier
  -> 更新机器人 anchor
  -> 重建当前窗口内候选边
  -> 扫描全部历史边并合并回来
  -> 转换完整 NavigationGraph
  -> 生成完整 RViz Marker
```

输入地图尺寸固定, 所以下列成本基本固定:

- GridMap 解码和分类
- 高程尖峰清理
- 脚下盲区修补
- free 连通分量计算
- obstacle 和 unknown 距离场
- Frontier cell 栅格扫描

下列成本会随历史图增长:

- 全部节点扫描
- 全部节点临时索引重建
- 全部 Frontier owner 验证
- 全部历史边合并
- 完整消息转换
- 完整图可视化

### 6.1 优化前后的总体变化

|---|---:|---:|---:|

| 导航图总平均耗时 | 1188 ms | 801 ms | 降低约 33% |

| Pipeline 中 graph 消息平均年龄 | 3057 ms | 1045 ms | 降低约 66% |

已有优化取得了实质效果, 但没有消除历史图增长带来的复杂度

### 6.2 单次运行中的增长

最近一次运行启动阶段:

```text

总耗时约 224 ms
```

地图分类耗时基本稳定, 图更新和消息转换持续增长, 说明主要问题不是固定局部 GridMap, 而是历史导航图相关的全局工作

## 7. 计划中的目标结构

### 7.1 持久节点空间索引

为 `GraphState` 增加长期存在的空间索引, 不再在每个阶段临时从全部节点重建

索引需要支持:

- 插入新节点
- 删除失效节点
- 更新移动的机器人 anchor
- 按矩形或圆形范围查询节点 ID
- 按半径查询 Frontier owner 和候选邻居

当前节点基本位于世界对齐 lattice 上, 因此持久空间哈希比每帧重建 KD-Tree 更容易维护

如果未来接入全局回环优化, 大量历史节点坐标同时变化时再触发一次显式全量索引重建

### 7.2 局部节点集合

每帧首先查询:

```text
local_node_ids = spatial_index.query(grid_bounds + safety_margin)
```

后续节点更新、局部 owner 构建和候选边生成只使用 `local_node_ids`

查询结果仍需通过 `world_to_grid` 做精确过滤, 空间索引只负责快速粗筛

### 7.3 活动 Frontier 集合

维护独立的 `active_frontier_owner_ids`

每帧只处理:

- 当前局部窗口内的活动 Frontier owner
- 上一帧活动但刚离开窗口的 owner
- 当前新检测到的 Frontier 附近 owner

刚离开局部窗口的活动 Frontier 按当前项目语义清除一次, 对应分支继续由 Planner 的 deferred branch 记忆

不应为了清除少量活动 Frontier 而扫描全部历史节点

### 7.4 邻接边索引

为 `GraphState` 增加:

```text
adjacency[node_id] -> incident edge keys
```

每帧受影响的边只包括:

- 局部节点已有的关联边
- 局部节点半径内可能新增的候选边
- 被删除节点的关联边
- 机器人 anchor 的关联边

远处历史边继续留在 `GraphState.edges`, 不再通过 `merge_historical_edges` 每帧复制回来

### 7.5 Dirty 集合

维护本帧变化集合:

- `dirty_node_ids`
- `removed_node_ids`
- `dirty_edge_keys`
- `removed_edge_keys`
- `dirty_frontier_owner_ids`

Dirty 集合用于:

- 精确更新缓存
- 输出诊断
- 判断是否需要立即发布完整图
- 后续可能实现增量消息

第一阶段仍保持当前 `NavigationGraph` 消息接口, 不要求下游立即支持增量消息

### 7.6 发布和可视化解耦

核心几何更新与完整图输出需要分开计时和调度

建议:

- 局部几何更新继续处理最新 GridMap
- 完整 `NavigationGraph` 保持兼容, 但只在拓扑变化、current node 变化或固定低频周期时发布
- 缓存稳定节点和边的消息转换结果
- RViz Marker 仅在存在订阅者时生成
- 完整历史图可视化使用更低频率
- 当前局部调试视图和完整历史图使用独立发布频率

即使缓存消息对象, ROS 最终序列化完整数组仍是全图成本, 所以完整图发布频率不能无限提高

## 8. 优化后的更新流程

```text
接收最新局部 GridMap
  -> 固定大小地图分类和距离场
  -> 空间索引查询 local_node_ids
  -> 只更新 local_node_ids
  -> 在当前窗口采样新节点并增量写入索引
  -> 检测当前局部 Frontier
  -> 只验证活动 Frontier 和局部 owner
  -> 更新机器人 anchor 和索引位置
  -> 通过 adjacency 查询受影响历史边
  -> 只验证或新建局部相关边
  -> 远处历史图保持不动
  -> 记录 Dirty 集合
  -> 按发布策略输出完整图
  -> 有订阅者时低频输出可视化
```

通俗地说:

> 当前实现每次修改一页地图前后都会翻阅整本地图册, 优化后只打开当前页, 历史页面原样保留

## 9. 必须保持的语义

性能优化不能改变以下行为:

- 历史节点拥有稳定 ID 和 UUID
- rolling GridMap 移动不会删除窗口外历史节点
- 当前窗口 unknown 不会否定历史边
- 当前可见障碍可以删除被明确阻断的历史节点或边
- 新边必须同时满足 obstacle 和 unknown clearance
- Frontier 离开当前窗口后不继续作为活动 Frontier 发布
- Planner 的 deferred branch 继续负责窗口外待探索分支记忆
- 机器人脚下盲区修补和 anchor 逻辑保持有效
- 输出图中 `current_node_idx` 必须指向合法节点

## 10. 实施顺序

建议按以下顺序实施, 每一步都可以独立验证:

1. 为现有图更新增加更细的节点、Frontier、边阶段耗时和工作量统计
2. 增加持久节点空间索引及一致性测试
3. 将旧节点更新限制到局部节点集合
4. 将采样去重和 current node 查询切换到持久索引
5. 增加活动 Frontier owner 集合, 移除 Frontier 全图扫描
6. 增加边 adjacency, 移除历史边全图合并
7. 将完整图发布和可视化从核心更新周期中解耦
8. 进行长距离仿真回归和性能对比

第一阶段不整体改写为 C++

如果完成局部化后, 固定局部计算仍无法满足真机频率, 再评估把距离场、Frontier 或边碰撞检查迁移到 C++

## 11. 验证和验收标准

### 11.1 正确性测试

- 多个 rolling window 连续移动后, 起点历史拓扑仍然存在
- 窗口外历史节点和边在本帧更新前后完全不变
- 当前窗口新障碍可以删除局部受影响边
- unknown 不能删除窗口外历史边
- 节点删除只清理关联边, 不改变其他节点 ID
- Frontier 离开窗口后只清理一次
- 新 Frontier 不会被重复分配给多个 owner
- anchor 移动时空间索引同步更新
- 输出完整图与优化前拓扑语义一致

### 11.2 性能测试

使用相同大小的局部 GridMap, 分别预填不同规模历史图:

```text
100 nodes
1000 nodes
5000 nodes
10000 nodes
```

核心局部更新时间应主要取决于窗口内节点数量, 不应随窗口外历史节点数量近似线性增长

分别记录:

- 地图分类耗时
- 局部节点查询耗时
- 节点更新耗时和节点数量
- Frontier 检测、验证和 owner 分配耗时
- 历史边验证和新边构建耗时
- 完整消息转换和序列化耗时
- RViz Marker 构造耗时
- Pipeline 中 graph 消息年龄

### 11.3 运行目标

第一阶段目标不是承诺某个固定毫秒数, 而是满足以下趋势:

- 历史图增长时, 核心图更新时间保持基本稳定
- 完整消息转换可以增长, 但不再阻塞每个局部地图更新
- graph 消息年龄保持稳定, 不随任务持续时间持续累积
- 关闭 RViz 或无人订阅时, 可视化阶段接近零成本

## 12. 2026-07-21 第一阶段实施记录

已完成:

- 为 `GraphState` 增加持久节点空间哈希
- 节点创建、移动和删除会同步空间索引
- 旧节点更新只遍历当前 GridMap 内节点
- 新节点采样直接通过持久索引去重

- Frontier owner 通过持久索引查询, 不再每帧重建全局 owner 索引

- 机器人轨迹走廊索引改为增量追加

- 历史边只更新 GridMap 及 edge radius 邻域的关联边
- 远处历史边保持原对象不动, 不再每帧复制合并
- 无 RViz 订阅者时跳过完整 Marker 构造
- 增加局部节点数、受影响边数和图内阶段耗时诊断


该检查使用小型合成 GridMap, 只证明远处 5000 个历史节点没有进入核心局部更新, 不能作为 Unity 或真机绝对性能结论
