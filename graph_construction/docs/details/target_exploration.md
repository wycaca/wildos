# 目标探索与分支恢复原理和优化方案

> 状态: 第一阶段已实现, Unity 短时回归通过, 待长任务复测
>
> 更新时间: 2026-07-22

## 1. 文档目的

本文解释 WildOS 在尚未发现目标时如何探索、发现目标后如何切换到目标接近、当前 Planner 如何保持探索分支和恢复死路, 以及为什么最近一次运行中出现多次不必要回头

本文重点回答以下问题:

- 视觉模型给 Frontier 打分后, Planner 如何决定机器人往哪里走
- 初始方向探索和真实目标接近有什么区别
- 社区实现和本项目当前实现有什么区别
- 当前复杂分支记忆为什么减少了左右摇摆, 又为什么可能导致大幅回头
- 后续如何保留死路恢复能力, 同时减少误判和不必要回退

## 2. 模块边界

目标搜索链路由多个模块共同完成:

```text
三相机图像和文本查询
  -> WildOS 视觉推理
  -> Frontier 视觉评分和目标 Mask
  -> 目标位置融合
  -> ObjectSearchGoalMux
  -> Graph Planner
  -> Path
  -> 局部控制器
```

各模块职责:

- WildOS 负责给几何 Frontier 提供视觉和语义分数
- `object_target_fusion` 负责从多视角和 LiDAR 形成目标位置估计
- `ObjectSearchGoalMux` 负责决定当前高层目标和搜索状态
- `graphnav_planner` 负责在 scored navigation graph 上选择路线
- 局部控制器负责执行路径和避障

本文主要讨论 `graphnav_planner` 的 Frontier 选择、路线保持和失败恢复, 不讨论目标 Mask 阈值和粒子滤波细节

## 3. 搜索状态和目标所有权

`ObjectSearchGoalMux` 是高层目标和完成状态的唯一 owner

主要状态:

```text
SEARCHING_WITH_INITIAL_GOAL
  -> TARGET_APPROACH_COARSE
  -> TARGET_APPROACH_METRIC
  -> TARGET_REACHED_VIEWPOINT
```

状态含义:

- `SEARCHING_WITH_INITIAL_GOAL`: 尚未获得可靠目标位置, 按初始方向探索
- `TARGET_APPROACH_COARSE`: 已有可用的视觉粗目标, 朝目标区域接近
- `TARGET_APPROACH_METRIC`: 已有稳定融合或 LiDAR 锁定目标, 朝实际目标接近
- `TARGET_REACHED_VIEWPOINT`: 已满足最终到达条件, 保持当前位置停止

Planner 收到搜索状态变化时会清除旧 goal 和旧探索分支, 等待同一状态的新 goal 后再规划

这样可以避免目标刚确认时仍短暂发布旧探索路径

## 4. Frontier 评分原理

每个 Frontier 候选的总代价主要由两部分组成:

```text
总代价 = 当前节点到 Frontier owner 的图路径代价 + Frontier 虚拟边代价
```

图路径代价表示机器人沿已知安全导航图走到 Frontier owner 的成本

Frontier 虚拟边代价综合:

- Frontier 后方未知空间与规划目标的关系
- 目标方向对应视觉 bin 的 Frontier 分数
- 配置中的视觉分数和距离权重

视觉分数越高, 对应方向越有可能是可探索开口或目标相关方向, 候选代价通常越低

目标附近已经存在图节点时, Planner 可以直接把这些节点连接到虚拟目标, 不必继续选择 Frontier

### 5.2 社区参考实现

本仓库保存的社区参考 Planner 位于:

```text
external_references/nebula2-wildos-main_ws/graphnav_planner
```

社区版本使用较早、较简单的 Frontier 滞回策略:

1. 每次图更新重新计算所有 Frontier 代价
2. 用 Dijkstra 选择总代价最低的 Frontier
3. 记录上一次选中的 Frontier 位置
4. 在 `path_smoothness_period` 时间内, 优先限制在上次 Frontier 附近的候选
5. 时间窗结束或附近没有候选时, 恢复全局选择

默认相关参数:

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `path_smoothness_period` | 10 s | 上次 Frontier 附近候选保持时间 |
| `local_frontier_radius` | 7 m | 认为属于上次局部方向的范围 |
| `min_local_frontier_score` | 0.4 | 保持局部候选的最低视觉分数 |

社区版本没有:

- 完整活动路线记忆
- 沿路线进度检测
- 路径失效连续确认
- 失败走廊冷却
- deferred branch 队列
- 初始方向探索专用模式
- 目标搜索状态切换时的路线重置

它可以概括为:

> 每次选择当前最优 Frontier, 短时间内优先保持上一次 Frontier 附近方向

优点:

- 逻辑简单
- 状态少
- 不容易被历史分支强制拉回很远的位置

缺点:

- Frontier UUID 或评分变化时容易切换路线
- 上次 Frontier 消失后可能立即选择另一侧
- 没有明确记住已经失败的走廊
- 遇到死路主要依赖下一帧重新全局规划
- 多个相近 Frontier 可能造成左右摇摆

### 5.3 本项目当前实现

当前实现增加了三层记忆:

1. `ActiveBranch`: 当前已经提交的探索路线
2. `DeferredBranch`: 当前没有选择但以后可能需要恢复的路线
3. `FailedBranch`: 已确认失败并处于冷却期的走廊

它可以概括为:

> 提交一条探索走廊并持续延伸, 其他路口先记住, 当前路线失败后再从记忆中恢复

这套策略解决了社区实现容易因单帧 Frontier 变化而左右摇摆的问题, 但也引入了误判失败和过度回退风险

## 6. 当前初始方向探索逻辑

当状态为 `SEARCHING_WITH_INITIAL_GOAL` 时, Planner 不把初始目标理解为必须到达的固定点

初始化过程:

1. 使用机器人当前位姿作为探索原点
2. 使用初始 goal Pose 的朝向作为固定探索方向
3. 使用初始 goal 与机器人距离作为前视距离
4. 固定探索方向, 后续不因机器人越过初始目标位置而反向

每次规划时生成移动虚拟目标:

```text
移动虚拟目标 = 初始原点 + 固定方向 * 当前前向进度 + 前视距离
```

候选 Frontier 会计算:

- 相对固定方向的前向进度
- 到候选路线最低投影点所需的回退距离
- 候选方向与固定探索方向的对齐程度
- 图路径和视觉 Frontier 总代价

初始阶段优先选择:

- 有足够前向进度
- 初始回退不超过限制
- 与固定方向同向

如果暂时没有满足要求的候选, 会等待 `directional_block_confirm_timeout` 确认前向方向受阻, 然后允许选择其他方向

## 7. Active、Deferred 和 Failed 分支

### 7.1 ActiveBranch

`ActiveBranch` 保存:

- Frontier UUID 和位置
- 路径节点 UUID
- 路径点
- 分支起始和最近进展时间
- 当前最大进度
- 路线末端方向
- 是否正在恢复 deferred branch

新图到来时, 如果新候选与活动分支属于同一 Frontier、共享路径前缀或同一走廊, Planner 会延伸原路线而不是重新选择全局最优候选

### 7.2 DeferredBranch

当前没有被选择, 但和已选方向不同的 Frontier 会被记录为 deferred branch

活动分支失败时, Planner 会优先尝试恢复 deferred branch

这让机器人在真正遇到死路时能够回到以前经过的岔路口

### 7.3 FailedBranch

活动分支因无进展或路径失效被释放时, 会记录失败走廊

失败走廊通过以下信息合并:

- Frontier UUID
- Frontier 空间位置
- 路线方向
- `frontier_failure_merge_radius`

同一走廊连续失败时会延长冷却时间, 避免立即重复进入同一个死路

## 8. 当前分支释放条件

活动分支主要在两种情况下释放

### 8.1 路径失效

如果当前提交路径中尚未走过的两个节点仍存在, 但它们之间的边消失, 则认为路径可能失效

持续超过 `path_invalid_confirm_duration` 后释放活动分支

当前配置:

```text
path_invalid_confirm_duration = 1.5 s
```

### 8.2 长时间没有进展

当前配置:

```text
frontier_progress_start_grace = 20 s
frontier_progress_timeout = 12 s
```

只有分支启动超过 20 秒后才允许无进展释放

初始方向探索的进度定义为:

```text
机器人位置在固定初始方向上的投影
```

目标接近中继分支的进度使用机器人在当前路径上的位置

## 9. 当前参数基线

当前 `graphnav_planner/config/planner.yaml` 主要参数:

| 参数 | 当前值 | 作用 |
|---|---:|---|
| `frontier_dist_cost_factor` | 2.0 | 无视觉分数时的 Frontier 距离权重 |
| `goal_dist_cost_factor` | 1.0 | 目标附近节点到目标的代价权重 |
| `frontier_score_factor` | 20.0 | 视觉分数对 Frontier 代价的影响 |
| `frontier_continuity_radius` | 5.0 m | Frontier 迁移仍视为同一路线的范围 |
| `frontier_progress_timeout` | 12.0 s | 无进展超时 |
| `frontier_progress_start_grace` | 20.0 s | 分支启动保护时间 |
| `directional_min_forward_progress` | 0.5 m | 初始前向候选最低进度 |
| `directional_max_initial_backtrack` | 2.0 m | 理想前向候选最大回退 |
| `directional_block_confirm_timeout` | 5.0 s | 前向候选缺失确认时间 |
| `frontier_failure_cooldown` | 60.0 s | 失败走廊基础冷却时间 |
| `frontier_failure_merge_radius` | 2.5 m | 失败走廊空间合并范围 |
| `path_invalid_confirm_duration` | 1.5 s | 路径失效确认时间 |
| `goal_radius` | 3.0 m | Planner 目标附近节点半径 |

`directional_max_initial_backtrack` 当前不是恢复阶段的硬限制, 这是日志中出现 4 至 5 米回退的重要原因

## 10. 最近一次运行记录

2026-07-21 13:27 左右启动的最近一次成功目标搜索持续约 15.3 分钟

任务最终成功进入目标锁定和完成状态, 但探索阶段存在明显路线恢复问题

### 10.1 目标状态

目标融合过程:

```text
PENDING
  -> TRACKING
  -> LIDAR_LOCKED
  -> REACHED
```

Planner 在 `TRACKING` 阶段没有切换高层目标

只有进入 `LIDAR_LOCKED` 后, Goal Mux 才从初始探索目标切换到真实目标, 随后约 9 秒进入 `REACHED`

因此探索阶段多次回头不是目标位置频繁跳变造成的

### 10.2 分支切换统计

日志统计:

- 因 `no_path_progress` 释放活动分支 19 次
- 因 `path_invalid` 释放活动分支 5 次
- 选择 `deferred_recovery` 22 次
- 至少 12 次选择了负前向进度分支
- 至少 8 次需要超过 2 米回退
- 部分回退距离达到约 4 至 5.5 米

这些事件与实际观察到的多次掉头一致

### 10.3 Planner 性能

Planner 单次计算通常为:

```text
平均约 14 至 35 ms
95% 上限多数约 30 至 50 ms
最大约 64 ms
```

Planner 不是当前 CPU 性能瓶颈

问题主要是行为策略, 不是 Dijkstra 计算太慢

部分 30 秒统计窗口中路径变化达到 12 至 19 次, 路线切换频率过高, 可能进一步影响局部控制器稳定执行

## 11. 当前逻辑的问题

### 11.1 固定方向投影不能完整表达真实进展

机器人绕障时可能需要:

- 横向移动
- 先转向再前进
- 沿弧线通过开口
- 短距离后退调整姿态

这些动作可能沿实际路径持续前进, 但在固定初始方向上的投影没有明显增加

因此正常绕障可能被误判为无进展

### 11.2 DLIO 和图暂停仍消耗超时时间

最近运行中 DLIO 出现多次姿态异常暂停, 导航图也存在约 0.8 至 1.2 秒消息年龄

如果定位、地图或控制器没有提供有效新状态, 无进展和路径失效计时不应继续累计

### 11.3 路径失效确认接近图消息延迟

当前路径失效确认只有 1.5 秒

当导航图自身可能落后约 1 秒时, 单次局部边抖动或短暂缺帧容易被当成真实路径失效

### 11.4 DeferredBranch 被优先处理

活动分支释放后, 当前逻辑先尝试 deferred branch, 再处理当前实时 Frontier

因此附近即使出现新的合理路线, Planner 也可能先回到以前记录的岔路口

### 11.5 回退限制不是硬约束

2 米回退限制只用于判断候选是不是理想前向路线

恢复阶段如果没有理想候选, 仍可以选择回退 4 至 5 米的历史分支

### 11.6 当前 Frontier 和历史分支不是统一评分

实时 Frontier 使用视觉分数、未知距离和图路径代价

历史恢复分支主要使用图路径和回退距离

两类候选不在同一代价尺度上, 历史分支可能显得异常便宜

### 11.7 失败走廊身份仍可能碎片化

Frontier UUID 会随局部地图和 owner 变化迁移

空间半径和方向合并能够缓解问题, 但相邻 Frontier 仍可能代表同一物理走廊却没有被合并, 从而绕过失败冷却

## 12. 计划中的优化原则

优化不回退到社区版本的简单定时滞回, 也不保留当前过强的历史分支优先级

目标是:

> 使用当前版本的路线连续性和死路记忆, 采用社区版本更简单的统一候选选择方式

核心原则:

1. 当前路线安全且机器人有实际进展时保持路线
2. 方向只用于候选偏好, 不单独作为失败判断
3. 定位、地图或控制器不健康时冻结失败计时
4. 当前 Frontier 和历史分支使用统一代价
5. 普通恢复阶段严格限制回退距离
6. 只有确认真实死路后才允许大幅回头
7. 目标锁定后清除与目标无关的探索记忆

## 13. 计划中的进度判断

初始方向投影继续用于表达任务偏好, 但不再作为唯一进度

活动路线进度主要使用:

- 机器人在提交路径折线上的弧长进度
- 到下一有效路点的距离是否减小
- 相对最近路径段的实际位移
- 固定初始方向投影, 仅作为辅助信息

通俗地说:

> 只要机器人确实沿当前路线绕过障碍并接近下一路点, 就算有进展, 不要求每一步都朝初始方向直走

路线进度需要使用单调最大值, 避免定位小幅抖动反复增加或减少进度

## 14. 健康状态门控

只有同时满足以下条件时才累计无进展或路径失效时间:

- DLIO 位姿健康
- odom 时间新鲜
- 导航图时间新鲜
- 当前存在有效提交路径
- 局部控制器正在执行当前路线
- 当前没有处于暂停或停止状态

任一条件不满足时:

- 保留当前活动分支
- 冻结进度超时
- 冻结路径失效确认
- 不记录失败走廊

这样可以避免把感知或定位暂停误认为路线失败

## 15. 计划中的路径失效确认

路径失效不能只依赖一次边消失

建议要求:

1. 导航图消息时间新鲜
2. 同一条尚未走过的边连续多帧消失
3. 持续时间超过至少 2 至 3 个有效图周期
4. 当前没有 DLIO 暂停
5. 当前机器人仍需要经过这条边

初步可以把确认时间调整到不低于 3 秒, 最终参数由图更新优化后的真实频率决定

## 16. 统一候选池和统一代价

活动分支释放后, 不再先选 deferred branch 再选实时 Frontier

候选池统一包含:

- 当前实时 Frontier
- 仍然有效的 deferred branch
- 目标方向中继 Frontier

统一代价建议包含:

```text
总代价 =
  图路径长度
  + Frontier 视觉和目标方向代价
  + 初始方向偏离惩罚
  + 回退距离惩罚
  + 路线切换惩罚
  + 失败走廊惩罚
  + 数据陈旧惩罚
```

历史分支必须重新获得当前 Frontier 信息或使用明确衰减的历史评分, 不能继续以缺少视觉代价的低成本参与竞争

## 17. 分级回退策略

普通候选选择阶段:

- `directional_max_initial_backtrack` 作为硬限制
- 超过限制的候选不进入普通候选池

如果没有合法前向候选:

1. 保持当前位置或低速原地观察
2. 等待新的局部地图和视觉评分
3. 确认当前方向持续被阻断
4. 再进入明确的 dead-end recovery 状态

进入 dead-end recovery 后:

- 允许逐级放宽回退距离
- 优先选择最近且未失败的岔路
- 每次只选择一个明确恢复目标
- 恢复完成前不因普通评分波动再次切换

大幅掉头必须有清晰日志:

```text
进入死路恢复, 原因=连续无进展或路径确认失效, 回退距离=..., 目标分支=...
```

## 18. 失败走廊合并

失败走廊不应只依赖 Frontier UUID

建议使用:

- 分支入口位置
- 路线前若干米的几何方向
- 路径共享前缀
- 走廊空间包络或代表点

同一物理走廊即使 Frontier owner 或 UUID 迁移, 也应命中同一失败记录

失败记录需要定期清理, 避免长时间任务无限增长

## 19. 目标出现后的逻辑

目标状态切换继续保持当前安全机制:

1. 清除初始方向探索状态
2. 清除与目标无关的活动和 deferred 分支
3. 等待对应状态的新目标
4. 如果目标附近有可达图节点, 直接规划到目标
5. 如果目标暂时位于图外, 选择能够接近目标的中继 Frontier
6. 中继 Frontier 仍使用统一候选代价和路线连续性
7. 目标位置小幅更新时尽量更新末端路线, 不重新选择无关探索分支

最终完成仍由 Goal Mux 的稳定目标和物理距离门控决定

Planner 的 `goal_radius` 停止路径是执行层保护, 不能替代目标融合和 Goal Mux 的完成判定

## 20. 优化后的整体流程

```text
尚未发现目标
  -> 按初始方向给实时 Frontier 排序
  -> 提交一条活动路线
  -> 使用路径弧长和路点接近判断实际进展
  -> 路线安全且有进展则持续执行
  -> 定位或图不健康则冻结判断
  -> 连续新鲜图确认失败后释放路线
  -> 实时和历史候选统一评分
  -> 普通恢复严格限制回退
  -> 无候选时先观察和等待
  -> 确认死路后进入分级回退
  -> 目标锁定后清除探索状态
  -> 直接接近目标或选择目标方向中继
  -> 到达观察点后停止
```

通俗地说:

> 正常绕障不会被误判卡住, 普通候选不会让机器人突然回头 5 米, 只有明确确认死路后才执行有解释的回退

## 21. 性能和日志要求

Planner 当前不是主要 CPU 瓶颈, 优化重点是行为稳定性

仍需保留低频统计:

- 规划调用频率
- 平均、95% 上限和最大规划耗时
- 30 秒内路径变化次数
- ActiveBranch 持续时间
- 实际路径进度和最后进展年龄
- 路径失效连续帧数
- DLIO、odom 和 graph 健康状态
- 实时 Frontier 和 deferred candidate 数量
- 最终选择的总代价分解
- 回退距离和回退状态
- 失败走廊数量和冷却命中次数

事件日志只在状态变化时输出:

- 选择新活动路线
- 延伸当前路线
- 冻结或恢复失败计时
- 确认路径失效
- 进入或退出死路恢复
- 选择大幅回退路线
- 从探索切换到目标接近
- 发布停止路径

不要在每帧重复输出相同路径和相同候选排行

## 22. 实施顺序

建议按以下顺序实施:

1. 增加路线弧长、下一路点距离、健康状态和失效连续帧诊断
2. 将无进展判断从固定方向投影改为路径进度
3. 在 DLIO、odom、graph 或 controller 不健康时冻结计时
4. 延长并改造路径失效连续确认
5. 将最大普通回退距离改成硬限制
6. 合并实时 Frontier 和 deferred branch 候选池
7. 统一候选代价和日志分解
8. 增加显式观察等待和 dead-end recovery 状态
9. 改进失败走廊几何合并
10. 进行重复场景和长距离目标搜索回归

## 23. 验证场景

### 23.1 正常绕障

机器人需要先横移再继续前进

预期:

- 路径弧长持续增加
- 不触发 `no_path_progress`
- 不切换到历史分支

### 23.2 短暂 DLIO 暂停

暂停 1 至 3 秒后恢复

预期:

- 活动路线保留
- 失败计时冻结
- 不记录失败走廊
- 恢复后继续原路线

### 23.3 导航图边短暂消失

单帧或少量帧缺少提交路径中的边

预期:

- 不立即释放活动路线
- 边恢复后清除失效计数

### 23.4 前方无候选但未确认死路

预期:

- 不立即选择 4 至 5 米后的历史分支
- 先观察和等待
- 普通候选遵守回退硬限制

### 23.5 真实死路

前方持续阻断且当前路径确认失效

预期:

- 进入明确 dead-end recovery
- 选择最近的未失败替代走廊
- 允许必要回头
- 不重新进入刚失败的走廊

### 23.6 目标在探索期间出现

预期:

- 目标在 `TRACKING` 但未满足 Goal Mux 门槛时继续稳定探索
- 进入稳定目标状态后只切换一次高层目标
- 清理旧探索分支
- 不恢复与目标无关的 deferred branch

## 24. 验收标准

- 正常绕障不因固定方向投影不足释放路线
- DLIO 和图暂停期间不累计失败时间
- 单帧边消失不触发路径释放
- 普通恢复不超过配置的硬回退距离
- 超过普通回退限制的路线只在明确 dead-end recovery 中选择
- 当前 Frontier 和历史分支使用同一代价尺度
- 同一物理失败走廊在 UUID 变化后仍被冷却
- 目标锁定后不恢复旧探索分支
- 相同场景路径变化次数显著低于当前 12 至 19 次每 30 秒的高峰
- 保持最终成功找到并到达目标的业务能力

## 25. 与导航图更新优化的关系

导航图局部增量更新和探索策略是两个独立模块, 但会互相影响

导航图更新过慢会造成:

- graph 消息陈旧
- 路径边短暂缺失
- Planner 更容易误判路径失效

探索策略过于敏感会放大这些输入抖动

推荐顺序:

1. 先增加两个模块的细粒度诊断
2. 完成导航图核心局部增量更新
3. 根据优化后的真实 graph 频率确定路径失效门槛
4. 完成探索进度、统一候选和分级回退优化

导航图更新设计记录在:

```text
graph_construction/docs/details/graph_update.md
```

## 27. 2026-07-22 第一阶段实现和 Unity 回归

### 27.1 已实现逻辑

- 无进展判断不再使用初始方向投影, 改为实际路径弧长、下一路点距离和沿执行路线的真实位移
- graph 或 odom 不新鲜时冻结分支失败计时, 恢复后重新开始连续确认
