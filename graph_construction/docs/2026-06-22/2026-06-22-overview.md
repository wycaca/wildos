# Graph Construction 初步理解

日期: 2026-06-22

目标: 先理解 `nasa-jpl/nebula2-wildos` 中未开源的 Graph Construction 模块, 明确它在 WildOS 系统中的作用, 公开代码暴露出的输入输出接口, 以及后续逐步复现的最小路线

## 当前结论

Graph Construction 是 WildOS 的几何记忆层, 负责把局部几何感知和可通行性结果增量组织成 `NavigationGraph`, 并发布给上层视觉语义导航模块和图规划器使用

公开仓库明确说明 Graph Construction 还未开源, 但它是部署时必须同时运行的外部组件之一, 与 `Elevation Mapping CuPy`, `DLIO`, `Nav2` 并列出现在 Required External Components 中

从已开源代码看, Graph Construction 的最小职责不是直接做语义决策, 而是稳定输出可被评分和规划的稀疏图, 其中包含 free node, frontier node, edge, traversability cost, explored radius, frontier points, current node index 等信息

## WildOS 中的位置

WildOS 的整体链路可以简化为:

```text
DLIO / elevation map / robot odom
        |
        v
Graph Construction -> /spot1/nav_graph
        |
        v
visual_navigation/wildos/nav.py
        |
        v
/spot1/scored_nav_graph
        |
        v
graphnav_planner -> graph path -> path follower -> Nav2 / local controller
```

`visual_navigation/wildos/nav.py` 订阅原始 `NavigationGraph`, 读取其中的 geometric frontier nodes, 将这些 frontier 投影到多相机图像, 再用 ExploRFM 输出的 traversability, visual frontier, object similarity 对 frontier 做按方向离散的评分

`graphnav_planner` 不直接使用原始 `/spot1/nav_graph`, launch 文件中把 `~/nav_graph` remap 到 `scored_nav_graph`, 因此 planner 实际消费的是视觉模块添加过 `frontier_scores` 的图

## 公开代码中的接口信息

`graphnav_msgs/msg/NavigationGraph.msg`:

```text
std_msgs/Header header
string[] trav_classes
Node[] nodes
Edge[] edges
uint32 current_node_idx
```

`Node.msg`:

```text
UUID uuid
geometry_msgs/Pose pose
NodeTraversabilityProperties[] trav_properties
KeyValue[] properties
```

`NodeTraversabilityProperties.msg`:

```text
bool is_frontier
geometry_msgs/Point[] frontier_points
float32 explored_radius
float32 free_radius
KeyValue[] properties
```

`Edge.msg` 和 `EdgeTraversability.msg`:

```text
uint32 to_idx
uint32 from_idx
EdgeTraversability[] traversability
KeyValue[] properties

float32 traversability_cost
KeyValue[] properties
```

`KeyValue.msg` 是一个轻量扩展字段:

```text
string key
float32[] value
```

当前 WildOS 默认使用 `trav_class = default`, 因此 Graph Construction 至少需要保证 `trav_classes` 包含 `default`, 并且每个 node 和 edge 的 traversability 数组顺序与 `trav_classes` 对齐

## Graph Construction 应该输出什么

基于公开接口, Graph Construction 第一阶段最小可复现输出是:

- `header.frame_id`, 图坐标系, 通常应与 odom 或 map 系一致
- `nodes`, 稀疏空间节点, 每个节点有稳定 `uuid` 和 3D pose
- `edges`, 节点间可走连接, `traversability_cost` 作为图搜索权重
- `current_node_idx`, 机器人当前所在或最近的 graph node
- `is_frontier`, 标记当前节点是否是探索边界
- `frontier_points`, frontier node 指向未知区域的一组边界点, planner 会取均值辅助生成末端 waypoint
- `explored_radius`, planner 会用它构建 unexplored space debug map, 并估计 frontier 到目标未知区域的代价
- `free_radius`, 可能用于描述节点附近局部可通行范围, 当前 planner 消费不明显, 但应保留

WildOS 视觉模块会在 frontier node 的 `properties` 中追加:

```text
key = frontier_scores
value = num_angular_bins 个方向评分

key = is_default_scored
value = [0.0] 或 [1.0]
```

这说明 Graph Construction 不需要自己生成语义 score, 但必须提供足够稳定的 frontier 几何信息, 让视觉模块能投影和评分

## 推测的内部原理

以下是基于论文描述和接口消费方式的推断, 不是公开代码确认的实现:

1. 输入局部 2.5D elevation map, odometry, TF, traversability layer
2. 从局部地图中提取 free space, obstacle / unknown boundary, frontier cells
3. 按距离或空间聚类生成稀疏 graph nodes
4. 给当前 free region 生成普通节点, 给 known / unknown 边界生成 frontier nodes
5. 用局部可通行性检查连接近邻节点, edge weight 由距离和 traversability cost 组成
6. 随机器人运动增量更新图, 移除或降级已经消失的 frontier, 保留历史 free nodes 作为空间记忆
7. 根据机器人当前位置更新 `current_node_idx`
8. 发布 `NavigationGraph`

这个模块的核心难点不是单次 frontier 提取, 而是增量一致性, 包括节点 UUID 稳定性, frontier 生命周期, 图连通性, 以及局部地图滑窗变化时的历史记忆维护

## 与论文的关系

WildOS 论文和项目页反复强调 sparse navigation graph 的两个价值:

- Spatial memory, 在长距离探索中记住已走过区域和未完成 frontier, 避免纯视觉策略在死胡同中反复震荡
- Safe geometric grounding, 视觉模型只负责给方向和 frontier 加语义偏好, 最终路径仍依赖几何图和局部规划保证可执行

论文中的系统分成五步: 增量构建 sparse navigation graph, ExploRFM 预测 visual traversability / visual frontiers / object similarity, 粒子滤波估计目标位置, 将 geometric frontier 投影到图像并评分, 最后由 hierarchical planner 在 scored graph 上规划

因此复现 Graph Construction 时应先满足几何图接口, 再考虑与语义评分的闭环效果

## 可参考开源项目

- `leggedrobotics/elevation_mapping_cupy`, WildOS 明确依赖的 GPU 2.5D elevation mapping, 可作为局部地图和 traversability layer 来源, https://github.com/leggedrobotics/elevation_mapping_cupy
- `leggedrobotics/wild_visual_navigation`, ETH 系列野外视觉可通行性项目, 重点参考视觉 traversability 与 elevation map 集成方式, https://github.com/leggedrobotics/wild_visual_navigation
- `RayFronts`, WildOS 致谢项目之一, 后续应重点确认其 frontier 标注或 frontier 检测思路, https://github.com/RayFronts/RayFronts
- `Autonomous Exploration Development Environment`, 公开论文描述了 local planner, terrain traversability analysis, waypoint following, visualization tools, TARE exploration planner, FAR route planner 的完整集成经验, https://arxiv.org/abs/2110.14573
- `FAR Planner`, 采用 visibility graph 动态更新, 对未知环境中的增量图维护和快速重规划有参考价值, https://arxiv.org/abs/2110.09460

## 分阶段复现路线

### 阶段 1, 消息接口和假图闭环

实现一个最小 ROS 2 node, 发布固定 `NavigationGraph`, 包含 3-5 个 free nodes, 1-2 个 frontier nodes, 连通 edges, `trav_classes = ["default"]`

目标是让 `visual_navigation/wildos/nav.py` 能订阅图, 让 `graphnav_planner` 能消费 `scored_nav_graph`, 不追求真实地图

### 阶段 2, 从 2D 或 2.5D grid 生成 frontier

先不接完整 elevation map, 用 occupancy / traversability grid 做离线或模拟输入

实现 free / unknown 边界检测, frontier clustering, node pose, frontier_points, explored_radius, edge cost

目标是稳定生成可视化正确的 graph, 并验证 planner 能选 frontier

### 阶段 3, 增量更新和空间记忆

加入机器人 odom, 当前节点匹配, 历史节点保留, 新旧 frontier 合并, frontier 消失处理

目标是避免每帧重建导致 UUID 抖动, 因为视觉模块会按 UUID 缓存 frontier score 和 scoring distance

### 阶段 4, 接入真实 elevation map

接入 `elevation_mapping_cupy` 或等价 grid map, 从 map layer 中读取 elevation, traversability, known / unknown mask

目标是将阶段 2 的 grid 逻辑替换为真实机器人局部地图输入

### 阶段 5, 与 WildOS 完整联调

联调 `/spot1/nav_graph`, `/spot1/scored_nav_graph`, `/spot1/model_visualization`, `/spot1/score_rings`, `graphnav_planner/path`

重点检查 frontier 投影是否落在相机视野内, `frontier_scores` 是否随视觉输出变化, planner 是否能根据 score 改变 frontier 选择
